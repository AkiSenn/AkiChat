# Markdown 表格主线程开销：单项维护

2026-10-25，基线为 `433e9b3`，延续未合并 PR #2；不修改供应商、输入、键盘、滚动、存储、版本或发布流程。

## 先核对现状

上一轮已实现稳定消息行、80ms传输快照合并、350ms流式Markdown节流、后台块解析、文本测量缓存、独立草稿与底部跟随。本轮没有假定这些旧问题仍存在，也未重复改写它们。

剩余的可定位路径是 `MarkdownTable.rows`：它是计算属性，每次访问都拆分全部行、列并清理空白。SwiftUI的行索引、列索引和单元格内容都会读取它，因此一个表格的主线程body计算可能触发数百次整表解析。已有后台Markdown解析只识别了表格块，没有准备单元格数据，所以没有消除这条路径。该开销只影响含表格的回答，不是所有设备卡顿的统一结论。

## 唯一优化

将原样的行列拆分算法移入已有 `MarkdownParser`，表格块一次准备并缓存不可变的 `tableRows`，随已有后台工作结果交给UI；`MarkdownTable`仅索引该数组。单元格仍使用原来的 `NativeRichText`，宽度、字体、链接、颜色、横向滚动和不齐行处理不变。流式表格每个已节流快照独立准备，不修改历史或网络数据。新增API均为已有Foundation/SwiftUI功能，最低版本14.0不变。

## 可复现实验

`AkiChatTests/MarkdownTablePerformanceTests/testCompareLegacyAndPreparedTableFirstLayout` 在同一个iOS模拟器进程中运行：

- 20行与100行、3列，固定414×896窗口；混合中文、粗体和链接。
- 测试内保留 `433e9b3` 原计算属性与原表格body，作为仅测试编译的对照，不进入应用产物。
- 两种路径先预热，再交替顺序执行4组，均实际挂载 `UIHostingController`、布局相同原生文本控件并处理20ms的既有异步高度反馈。
- 校验新旧原生单元格文字和数量相同，记录原路径实际整表解析次数/解析耗时、两路径首次布局耗时、新路径准备耗时。
- 在日志中搜索 `TABLE_LAYOUT_BENCHMARK` 获取逐组JSON数据；不以不稳定的绝对毫秒阈值决定测试通过。
- 另有表格格式/流式末行保留、后台准备并在主线程交付两个必要回归测试。

准备耗时单列，不把它藏入“零开销”结论。首次布局不等于完整聊天滚动、键盘、流式交互或FPS；比较结果只用于判断这个剩余路径的收益。具体实际结果和CI链接记录于PR，不引用上轮静态页面Profiler作为本轮改进证据。
