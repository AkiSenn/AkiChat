# 模型状态、目录与保存的四项优化

2026-10-25，基线 `3dec614`（已发布的1.2.0代码），本轮不推送版本标签、不覆盖公开IPA、不修改Bundle ID、最低iOS14或数据格式。

## 改动与边界

1. AppStore的消息变更默认仍刷新ChatPresentation。模型、思考/推理强度、会话参数、摘要选择和用量校准走明确的metadata路径，跳过消息遍历。保留原有状态通知、模型能力应用、上下文预算和原始历史。
2. 模型面板与模型管理共用ModelListCache。每份目录只排序一次，缓存当前搜索词的全部结果和收藏子集；提供商/目录变化失效。NSCache最多4个服务商、8MiB数组估算成本，内存压力时可丢弃重建，不保留无限查询历史。首次缓存未命中仍会排序，不声称所有冷开面板已无开销。
3. /models的JSON解析和目录合并使用可取消的串行后台OperationQueue，主线程只取快照、校验版本与提交结果。按ID索引替代反复first/contains，预期复杂度由二次增长降至线性。第一条重复缓存记录、手动模型、收藏、排序、能力覆盖、提示词及缺失旧模型规则与原算法一致。合并时若本地目录已改变，按最新快照最多再合并3次；持续冲突提示重试，取消/删除Provider后丢弃结果。网络失败、空列表仍保留已有配置。
4. 保留conversations.v1/providers.v1/settings.v1/catalogs.v2四个记录键。首次初始化完整保存，后续仅捕获、编码和写入脏域；写入按现有串行队列排序。失败的域及尚未写的域保留脏标记，下次保存重试最新值；后台先提交草稿，再等待已排队写入。磁盘不可用时仍会提示失败，不承诺异常情况下零数据丢失。

聊天域变化仍编码整个会话集合，本轮没有引入按消息/会话拆库迁移。减少的是未变服务商、设置、模型目录与聊天域之间的连带写入。JSON编码与Core Data保存仍在后台，不把它们错误描述为原来在主线程执行。

## 可复核测试

StateOptimizationTests验证：500条历史在模型/参数变化时不调用reconcile、真实消息清空仍更新、排序/过滤复用与目录失效、脏域写入范围、失败后重试、写入期间新草稿保留、合并语义、后台工作/主线程交付、处理期间本地编辑重合并、取消/删除服务商拒绝过期结果。网络使用MockURLProtocol，不需要真实Key。

StateOptimizationBenchmarks在同一模拟器进程里交替比较4组样本：

- 100/500消息各24次模型切换：旧路径由真实选择操作加上原有全历史reconcile构成；新路径使用同一AppStore选择操作。记录状态处理耗时和实际reconcile次数，不包括完整SwiftUI绘制。
- 1000模型20次读取：旧路径每次过滤排序，新缓存包含首次建缓存成本，检查结果一致、排序/过滤次数。
- 2000远端/2000缓存模型：测试文件保留原合并函数，与新索引算法逐字段比较，并记录合并耗时。
- 500条消息/1000模型的保存：比较原四域编码与新实际写入的JSON字节数、记录数。这里的字节数不是SQLite文件大小或真实闪存延迟。

日志标记为 `STATE_OPTIMIZATION_BENCHMARK`。计时为Debug/-Onone的局部工作量，不是FPS、实机延迟或完整键盘交互的提升比例。DEBUG计数器不通知UI，Release中不包含它们。具体测量数值与CI链接以本次实际日志为准。

这是局部算法/状态路径对照，不是两份完整App的端到端对比。旧模型切换基线由同一选择操作加原有reconcile构成，未测量FPS、实机动画、网络延迟或整页响应时间。
